`project.md`의 화면 골격을 눈으로 확인하기 위한 정적 목업입니다. React 의존성이 없어
브라우저에서 HTML 파일을 그대로 열면 됩니다.

- 확정 기준: `.ai/project.md` §15(기획), §22-§23(Issue 3·4), §28(디자인/스타일 기준), §31(자산 화면)
- 목표: 와이어프레임 합의 → 확정 디자인을 React + antd 6 + Apache ECharts로 이관

## 카드내역 가져오기 (§29)

`expenses.html`에서 카드사 CSV를 올려 정규화 행으로 가져온다.

- 파서·형식 판별·카드사 판별은 `common/card-import.js`가 한다. 이 파일은
  `samples/card/tools/build-card-import-bundle.mjs`가 만든 **자동 생성 파일**이다.
  파서 원본은 `apps/frontend/src/lib/card/`에 있고, 이 번들은 그 사본이다.
  파일이 안 열리면(ESM import 오류 등) 번들을 다시 생성한다.
- 흐름: CSV 선택 → 매직 바이트 판별 → 카드사 판별(계약의 `detect` 시그니처) →
  파싱 → 가맹점별 용도구분 → 가져오기.
- 암호화된 파일(비밀번호로 잠긴 문서)은 여지 않는다. 카드사에서 암호화 없는
  CSV로 받거나 엑셀에서 다시 저장해서 올린다. 비밀번호 입력란도 없다 —
  열기 구현이 없는데 입력만 두면 사용자를 속인다.
- 가맹점 용도(업무용/개인용)는 규칙으로 저장되어 다음 명세부터 자동 적용된다.
  미분류 행은 어느 합계에도 들어가지 않는다.
- 가져온 내역은 `assetflow.cardImports.v1` 키로 localStorage에 남는다.
  지출 항목(`assetflow.expenses.v1`)과 별개 계층이고, 지출 지표에는 자동으로
  섞이지 않는다. 카드 부가세 합계가 세금계산서 매입세액(320,000원/월)과
  직접 대조되지 않는 갭은 알려진 문제로 그대로 둔다.

## 검증 (눈으로만 확인하지 않기)

프로토타입도 회귀 테스트를 갖는다. 의존성 0개, `package.json` 없음(§30.4) —
`node` 하나만 있으면 돌아간다.

```
node design/prototype/tools/run-all.mjs
```

| 스위트 | 검증 대상 | 건수 |
|---|---|---|
| `test-mock-data.mjs` | 계층 저장 왕복, 깨진 저장소 필터, 계산 단일 출처 | 31 |
| `test-assets-page.mjs` | 읽기/수정 모드, 확정/취소, 새로고침 후 유지, 수익률 재계산 | 87 |
| `test-all-pages.mjs` | 6개 화면 기동, Filing 소진(null) 상태, 깨진 저장소 | 39 |

- 실패하면 `process.exitCode` 가 1 이라 그대로 CI 에 걸린다.
- 기대값은 **시드에서 계산**한다. 합계 숫자를 손으로 박지 않는다 —
  시드를 고쳤는데 테스트만 옛값을 요구하는 사고를 막는다.
- `prototype-harness.mjs` 가 `node:vm` 위에 최소 DOM 을 올린다. 화면이 **실제로**
  쓰는 API 만 담았다. 화면이 쓰지 않는 API 를 미리 구현하면 그 API 가 없어도
  아무도 모른다.
- 스크립트는 **문서에 적힌 순서대로** 실행한다. `mock-data.js` 를 미리 한 번 더
  적재하면 이중 실행이 되어 시드로 덮어쓴다(실수로 만든 함정, 주석에 남겼다).
- 카드 파서·번들 테스트도 같은 원칙으로 경로를 상대 경로로 푼다:

```
node samples/card/tools/test-parse-samsung.mjs
node samples/card/tools/test-parse-hyundai.mjs
node samples/card/tools/test-card-ui.mjs
```

실제 카드 명세는 개인정보라 저장소에 없다. 로컬에서만 대조하려면 환경변수로
경로를 준다. 주지 않으면 해당 검사만 **"건너뜀"** 으로 끝나고 실패로 세지 않는다.

```
$env:ASSETFLOW_CARD_REAL_DIR = "C:\Users\<you>\Downloads"
```

CI(`.github/workflows/quality-gate.yml`)는 위 명령들과 생성물 드리프트 검사까지
같은 순서로 돌린다. 앱(React/Spring) 빌드는 아직 워크플로에 없다 — 빌드 파일이
존재하지 않는다. 없는 걸 돌아가는 척하지 않는다.

### 지출 목록에 없는 사업 비용이 있다

매입세액 320,000원을 역산하면 매입 규모가 드러납니다.

```
매입세액                320,000원
→ 매입 공급가액 = 320,000 × 110/10 = 3,520,000원
지출 목록 합계                        2,053,753원
목록에 없는 사업 비용                1,466,247원
```

업태는 **컴퓨터수리업**이지만 실제 수입은 **소프트웨어 개발 용역**입니다.
따라서 컴퓨터 부품비가 반드시 있는 것은 아닙니다.

> 다만 인정 매입세액에는 실제 세금계산서가 있으므로, 매입 공급가액
> 3,520,000원/월은 **실재하는 사업 비용**입니다. 부품비라고 단정할 수는
> 없지만, 없는 금액도 아닙니다. 성분을 임의로 추측하지 않고 **미분류**로
> 두었습니다.
>
> 3,520,000원은 부가세 **제외** 금액입니다. 세금을 포함한 인voce 총액은
> 3,872,000원이고 매입세액 320,000원은Filing으로 회수합니다. 비상금 분모에
> 순사업비용(3,520,000원)과 인voice 현금(3,872,000원) 중 무엇을 쓸지는
> §28.7에서 확정해야 합니다. 현재는 순사업비용을 씁니다.

이 때문에 지표가 두 가지로 갈립니다.

| | 지출 목록 기준 | 매입 규모 기준 (보수적) |
|---|---|---|
| 월 사업 비용 | 2,053,753원 | **3,520,000원** |
| 월 순수익 | 6,146,247원 | **4,680,000원** |
| 비상금 유지 개월 | 18.9개월 (필수지출 기준 2,013,753원) | **10.8개월** |

`purchaseReconciliationGap` / `unclassifiedBusinessCost` /
`emergencyMonthsOnPurchases`로 코드에 노출했고, 대시보드에도 경고로 표시합니다.

목록 합계가 매입 규모 3,520,000원을 넘어서면 성질이 반대입니다. 이때는
`overStatedList`로 경고하고 보수적 기준도 목록 쪽(`max(목록, 매입규모)`)을
따라갑니다. 작은 쪽을 쓰면 비상금이 부풀려지므로 두 값을 모두 만족해야 합니다.

## 현금은 3계좌다 (§28.7)

현금을 합쳐서 "현금 1개"로 보면 안 됩니다. 계좌마다 쓸 수 있는 성격이 다릅니다.

| 계좌 | 금액 | 성격 | 비상금 분자 |
|---|---|---|---|
| 투자금 | 38,000,000원 | 순수 사용가능 | **포함** |
| 자동이체 | 12,400,000원 | 고정지출 배정분, 월중 소진 | 제외 |
| 부가가치세 | 28,500,000원 | 세금 적립 보관, Filing 대기 | 제외 |

총 현금 78,900,000원 중 **48.2%만 지금 쓸 수 있습니다.** 이게 대시보드의 핵심 숫자입니다.

비상금 유지 개월은 투자금만으로 계산합니다. 총 현금을 분자에 넣으면 쓸 수 없는 돈으로
유지 개월이 부풀려집니다. 자동이체 잔액을 더하면 분모(월 필수지출)와 이중 계상됩니다.

## 지출 화면이 단일 출처다 (§28.7)

`expenses.html`이 실제 항목과 값의 단일 출처입니다. 대시보드·설정 화면은
여기서 계산된 값만 읽습니다. `settings.html`의 월 필수지출은 읽기 전용이며
직접 고칠 수 없습니다.

| 화면 | 읽는 값 |
|---|---|
| 대시보드 | 비상금 유지 개월, 월 수지, 매입 대조 경고 |
| 설정 | 월 필수지출과 그 계산 근거 |

계산 흐름은 `mock-data.js` 한 곳에 있습니다.

```
AF.recompute()      파생값 전부 재계산
AF.storage.load()   저장값을 읽어 시드 대체 (깨진 값이면 시드로 되돌림)
AF.storage.save()   값을 바꾼 뒤에만 저장
AF.storage.reset()  시드 복구 + 저장소 삭제
AF.seed             초기값 원본
```

- `expenses.html`은 `AF.storage`만 호출합니다. localStorage를 직접 다루지 않습니다.
- 화면을 열기만 해서는 저장소가 생기지 않습니다. 값을 바꿔야 저장됩니다.
- 항목 금액·필수 여부·매입세액 공제 여부·이름, 미확정 항목 금액, 추가·삭제 모두
  저장 대상입니다. 이름은 바꿀 때 다른 입력의 `aria-label`도 함께 갱신합니다.
- 저장값이 손상됐으면 조용히 무시하지 않고 시드로 되돌립니다. 음수 금액은 0으로
  봉정하고, `essential`·`vatDeductible`가 없으면 필수로 간주합니다.
- 목록 합계가 매입 규모 3,520,000원을 넘으면 `overStatedList`로 경고합니다.
- 목업이라 localStorage(키 `assetflow.expenses.v1`)에 남습니다. 실제 구현에서는
  이 계층이 서버 API로 교체되고 이력 관리가 붙습니다.

## 자산 화면이 값의 단일 출처다 (§31)

`assets.html`이 금융자산·부채와 투자금의 단일 출처입니다. 대시보드는 여기서
계산된 값만 읽습니다. 지출 화면과의 관계가 §31.2 로 정리돼 있습니다.

| 값 | 조작 | 단일 출처 |
|---|---|---|
| 금융자산 행 | 편집·추가·삭제 | 자산 화면 |
| 부채 행 | 편집·추가·삭제 | 자산 화면 |
| 투자금 | 편집 | 자산 화면 (비상금 유지 개월의 분자) |
| 자동이체 잔액 | **읽기 전용** | 지출 화면 |
| 부가가치세 잔액 | **읽기 전용** | Filing 로직 |

- 총자산·총부채·순자산·총 현금·구성비는 **저장하지 않습니다.** 행에서
  `AF.recompute()`로 다시 만듭니다. 합계를 저장하면 행 편집과 어긋납니다.
- 저장은 **금융자산 목록, 부채 목록, 투자금 3개뿐**입니다(키 `assetflow.assets.v3`).
  자동이체·부가가치세 잔액을 저장하면 진짜 출처를 덮어씁니다.
- 저장하지 않는 시점이 있습니다. 화면을 열기만 해서는 키가 생기지 않고,
  **초기값 복구**는 키를 지웁니다(복구한 흔적을 남기지 않습니다).
- 항목을 전부 지운 0행은 정상 상태로 유지합니다. 반대로 목록이 비어 있지
  않은데 살아남는 행이 하나도 없으면 손상으로 보고 시드로 되돌립니다.
- 행 목록을 렌더한 뒤 배열 참조를 캐시하지 않습니다. 초기값 복구가 배열을
  새로 만들기 때문에 목록은 그때그때 읽습니다.

```
AF.assetStorage.load()   저장값을 읽어 시드 대체
AF.assetStorage.save()   편집 뒤에만 저장
AF.assetStorage.reset()  시드 복구 + 저장소 삭제
```

### 부채 행과 상환 계획

부채는 자산과 **같은 방식**으로 다룹니다. 읽기/수정 모드, 확정·취소, 합계 재계산이
전부 같습니다. 다른 것은 표의 열뿐입니다.

| 열 | 내용 |
|---|---|
| 항목 | 이름 |
| 기관 | 기관 선택 (없는 기관을 가리키면 `기타` 로 되돌립니다) |
| 유형 | `주택담보대출` 같은 분류 |
| 금액 | **남은 잔액**. 원금이 아닙니다 |
| 금리 | 연이율(%) |
| 만기 | 남은 회차에서 나온 달(YYYY-MM). 저장하지 않습니다 |
| 월납입액 | 은행이 실제로 청구하는 값 |
| 삭제 | 수정 모드에서만 |

- **만기를 따로 저장하지 않습니다.** `만기 = asOf + 남은 회차` 라는 한 가지 관계만
  두어 두 값을 따로 고치면 어긋나는 일을 막습니다. 만기 칸을 비우면 남은 회차가
  0이 되고 읽기 모드 칸은 `—` 가 됩니다. `asOf` 이전 납입일은 거절합니다.
- 상환 방식은 **원리금균등 하나**입니다(§34.6 결정). 월 필수지출이 고정값 하나라
  회차마다 달라지는 원금균등·만기일시를 못 받습니다.
- 월납입액은 **사용자가 준 값을 씁니다.** 공식 역산값과 0.78원 어긋나는데,
  역산값으로 갈아끼우면 지출 시드의 `대출상환및이자 317,180원`과 화면이 어긋납니다.
- 표 아래 **상환 계획**은 저장하지 않고 행에서 매번 다시 계산합니다.
  만기·남은 회차·다음 납입액(이자+원금 분해)·남은 이자·총 납입액·마지막 회차입니다.
  잔액만 갚아 계약 회차보다 먼저 끝나면 `예상 상환 완료 N회차` 로 그 사실을 보입니다.

### 읽기와 수정을 나눈 이유

기본값은 **읽기**다. 값이 들어간 표에 입력칸이 늘그러해 있으면, 값이 실수인지
편집 중인지 화면만 보고는 알 수 없다.

- 읽기 모드: 값은 텍스트. 행 조작 버튼도 없다(읽기 화면에 파괴 버튼을 두는 것은
  오조작의 여지다).
- 수정 모드: 값이 입력칸이 되고, 행마다 추가·삭제 버튼이 생긴다.
- **확정**을 눌러야 저장된다. 수정 중에는 `AF.assetStorage.save()` 를 부르지
  않으므로 새로고침하면 수정 전 값으로 돌아온다.
- **취소**는 진입 직전 스냅샷(금융자산·기관·상품유형·부채)을 되돌린다. Escape 도
  취소와 같다. 변경이 없을 때는 확인창 없이 조용히 닫는다 — 버릴 것이 없다.
- 확정/취소는 **변경이 있을 때만** 열린다. 아무것도 안 한 상태에서 취소가 가능하면
  그건 아무 일도 안 하는 버튼이다.

### 원금은 유형마다 다른 칸이다

| 유형 | 원금 | 입력 |
|---|---|---|
| 예적금·적금·CMA·ISA·연금 | 누적 납입액 | 직접 입력 (`principalDeposit`) |
| 주식·ETF·채권·펀드 | 수량 × 평단가 | **입력칸 없음.** 수량·평단가를 고치면 따라온다 |
| 그 외 | 일반 원금 | 직접 입력 (`principal`) |

투자자산 원금을 손으로 넣게 하면 수량·평단가와 어긋난 채로 방치된다. 그래서
원금칸을 읽기 전용으로 두고 계산값임을 표시한다. **원금은 저장된 값을 신뢰하지
않고 수량 × 평단가에서 다시 만든다** — 저장값을 읽으면 수량을 고친 뒤에도
원금칸과 수익률이 동시에 거짓말을 한다.

수익률은 어느 경우에도 직접 입력하지 않는다. 원금과 평가금액에서 계산한다.
실제 손실은 음수 수익률로 남는다 — 합계 계산에서 음수를 잘라내지 않는다는 뜻이다.

## 대시보드의 "다음 Filing"은 null 이 될 수 있다 (§31.5)

마지막 Filing 이 지나면 `nextFiling()` 이 `null` 을 반환합니다. 이건 예외가 아니라
정상 상태이므로 화면이 대비해야 합니다.

- `AF.recompute()` 가 `vat.upcoming` 을 함께 다시 정합니다. 로드 시 1회만
  정해두면 Filing 일정을 바꿔도 카운트다운이 낡습니다.
- 대시보드는 `up` 이 없으면 카운트다운 자리에 **"예정 없음"** 을 두고 다음
  Filing 등록을 안내합니다. `up.month` 를 바로 읽으면 `null` 접근으로
  화면 전체가 죽었습니다.
- `assets.html` 의 상태 미리보기 버튼 4개로 데이터/로딩/빈 데이터/오류를
  전환해 볼 수 있습니다. `dashboard.html` 과 같은 버튼입니다.

| `supplyExVat` (월 공급가액) | 8,200,000원 | 세금계산서 발행액 − 부가세 |

### 사용자 근거와 코드가 일치하는지 (전 항목 검증)

사용자가 제시한 실제 신고 내역과 계산 결과가 일치해야 합니다.

| 항목 | 사용자 근거 | 계산 결과 | 일치 |
|---|---|---|---|
| 6개월 매출세액 | 4,920,000 (= 820,000 × 6) | 4,920,000 | ✓ |
| 6개월 매입세액 | 1,920,000 (= 320,000 × 6) | 1,920,000 | ✓ |
| 6개월 납부세액 | 3,000,000 | 3,000,000 | ✓ |
| 실제 고지서 | 예정 1,500,000 + 확정 1,500,000 | 3,000,000 | ✓ |
| 4,920,000 − 3,000,000 | 1,920,000 ("남는 금액") | 1,920,000 | ✓ |

> **1,920,000원은 매입세액이면서 동시에 과다 적립액입니다.**
> 적립 820,000 − 납부 500,000 = 320,000 = 매입세액이라, 반기 누적액이 정확히
> 1,920,000원이 됩니다. 우연이 아니라 적립식이 매출세액 기준이라 생기는 구조입니다.

### 사업소득 8,200,000원은 순수익이 아니라 공급가액이다

사용자가 말하는 "사업소득 8,200,000원"은 필요경비를 차감한 순수익이 아니라
**공급가액(부가세 제외 매출)** 입니다. `9,020,000 = 8,200,000 + 820,000` 이기 때문입니다.

따라서 월 수지는 공급가액에서 지출을 빼야 합니다. 부가세 820,000원은 현금으로 쓸 수
없으므로 공급대가(9,020,000)가 아니라 공급가액(8,200,000)에서 뺍니다.

### 용어 정리

| 용어 | 뜻 |
|---|---|
| 공급가액 | 부가세 **제외** 매출 (이 사용자의 8,200,000원) |
| 공급대가 | 부가세 **포함** 매출 (9,020,000원) |
| 매출세액 | 공급대가 × 10/110 (820,000원) |
| 매입세액 | 매입하면서 낸 세액 (320,000원) |

`10/110`은 **공급대가**에 곱해야 합니다. 공급가액에 10%를 다시 곱하면 이중 계상입니다.
현행 적립액 820,000원은 결과적으로 맞지만 근거가 다릅니다 — 적립액은
"공급가액 × 10%"로 계산했으나, 실제로는 "공급대가 ÷ 11"입니다. 우연히 같았을 뿐입니다.

### 실제 산식

```
납부세액(공제 전) = 매출세액 − 매입세액
카드 발행세액공제  = 카드매출 공급대가 × 공제율   (연 한도, 납부세액 이내)
실제 납부세액      = 납부세액(공제 전) − 카드 발행세액공제
```

### 실제 산식 결과

```
매출세액       = 9,020,000 × 10/110   = 820,000원
매입세액                            −  320,000원
월 납부세액(공제 전)                 =  500,000원
연 납부세액                         =  6,000,000원
```

### 카드 발행세액공제 (부가가치세법 제46조) — 현재 미신청

| 항목 | 내용 |
|---|---|
| 업종 | 컴퓨터수리업 → 음식점·숙박업 아님, **1.3%** 적용 |
| 대상 | 개인사업자, 직전연도 공급가액 10억원 이하 (법인 제외) |
| 기준 | **카드·현금영수증으로 받은 매출**의 공급대가 |
| 공제율 | 1.3% (2026년 말까지) / 음식점·숙박업 등 2.6% |
| 한도 | 연 1,000만원 (2026년 말까지) |
| 환급 | **불가**. 납부세액을 0원으로 만드는 범위까지만 |

> 카드매출 5,000,000원 × 12 = 60,000,000원 × 1.3% = **780,000원(연)**.
> 한도 1,000만원과 납부세액 6,000,000원 어느 쪽에도 걸리지 않으므로 **780,000원 전부**가 가능합니다.

> ⚠ **실제 고지서에는 이 공제가 반영되어 있지 않습니다.**
> 실제 고지서는 반기 1,500,000 + 1,500,000 = 3,000,000원으로, 공제를 차감하기 전
> 납부세액(3,000,000원)과 일치합니다. 즉 지금은 공제를 신청하지 않고 있습니다.
> 신청하면 납부세액이 연 780,000원 줄어듭니다. `cardCreditClaimed: false`로 두고,
> UI에 **미신청 경고**를 표시합니다.

> 공제율과 한도는 세법 개정으로 바뀝니다. 코드에서는 `taxPolicy` 객체로 분리해
> 상수로 박지 않았습니다. 2026 세제개편안에 따라 2027년부터 1.2%·연 500만원으로
> 변경될 예정이며 확정 여부는 확인이 필요합니다.

### 신고는 반기 단위다

12분의 1이 아니라 **반기(6개월) 단위**로 고지합니다.

| | 산식 | 금액 | 시점 |
|---|---|---|---|
| 1기 = 1~6월 실적 | | | |
| 1기 예정고지 | 직전 반기 실제 납부세액 × 1/3 | 1,500,000원 | 4월 |
| 1기 확정고지 | 1기 실제 − 예정고지 | 1,500,000원 | 7월 |
| 2기 = 7~12월 실적 | | | |
| 2기 예정고지 | 직전 반기 실제 납부세액 × 1/3 | 1,500,000원 | 10월 |
| 2기 확정고지 | 2기 실제 − 예정고지 | 1,500,000원 | 1월 |

예정고지가 1,500,000원이 되려면 **직전 반기 실제 납부세액이 4,500,000원**이어야 합니다
(`4,500,000 ÷ 3 = 1,500,000`). 매출이 절반기별로 달라서 그렇습니다. 매출이 일정한
상태라면 예정고지는 1,000,000원·확정고지는 2,000,000원으로 나뉩니다.
`noticeFormulaCheck`로 공식이 실제 고지서를 재현하는지 검증합니다.

연 4회 합계 6,000,000원 = 실제 납부세액과 일치합니다.

### 과다 적립

| | 월 | 연간 |
|---|---|---|
| 적립액 (매출세액 기준) | 820,000원 | 9,840,000원 |
| 실제 납부 | **500,000원** | **6,000,000원** |
| 차액 | 320,000원 | **3,840,000원** |
| 카드공제 신청 시 납부 | 435,000원 | 5,220,000원 |
| 카드공제 신청 시 차액 | 385,000원 | **4,620,000원** |

적립액이 **매출세액(=820,000원)** 기준이라 매입세액 320,000원을 반영하지 않습니다.
결과적으로 1년간 **3,840,000원**이 쌓이고, 적립액의 39.0%입니다.

> Filing 후 이체 대상은 카드 발행세액공제분 780,000원이 아니라
> **3,840,000원**입니다. 공제를 신청하면 **4,620,000원**이 됩니다.

선택지는 세 가지입니다.

1. **그대로 두기** — 반기마다 1,920,000원이 쌓이고 Filing 후 전액 이체한다.
   고지액을 미리 알 수 있어 현금 흐름 예측이 쉽습니다.
2. **카드공제 신청** — 납부세액이 연 780,000원 줄어듭니다. 2026년 말까지 가능.
3. **적립액을 실제 납부세액(500,000원)으로 낮추기** — 고지 직전에만 금액이 모입니다.
   이 경우 `monthlyAccrual`을 500,000원으로 바꾸면 잔액은 0원이 됩니다.

자동 이체는 한국투자증권 API와 이체 권한이 필요해 현재 MVP 범위 밖입니다.

- **월 필수지출 단일 출처**: 지출 내역 합계(2,053,753원) 하나만 씁니다.
  대시보드 분모와 `settings.html` 초기값이 같은 값을 읽습니다 (§28.7).
- **종합소득세는 미확정**: 보통 0원이나 납부되는 달이 있습니다. `notIncluded`에
  `amount: null`로 남겨 두었고, UI는 **"세금 미반영"** 경고를 표시합니다.
  0원을 넣어 지표를 조작하지 않습니다.
- **지출 목록에 잡히지 않은 사업 비용이 있습니다**: 매입세액이 함의하는 매입 규모는
  3,520,000원으로 지출 합계 2,053,753원보다 1,466,247원 많습니다. 업태는 컴퓨터수리업이지만
  실제 수입은 소프트웨어 개발 용역이라 부품비 여부는 불확실합니다. 성분을 추측하지 않고
  미분류로 두었으며, 비상금은 **10.8개월(보수적) ~ 18.9개월(목록 기준)** 범위입니다 (§28.7).
- **카드 발행세액공제를 신청하지 않고 있습니다**: 연 780,000원이 줄지 않습니다.
  실제 고지서가 이를 반영하지 않으므로 `cardCreditClaimed: false`로 두고
  UI에 경고를 표시합니다.
- **세금 계좌는 한투 발행어음 CMA**: 은행 예금이 아니라 증권사 발행어음 상품입니다.
  이자는 발생하나 Filing 전에는 인출하지 않습니다. 사용자는 순수 현금보다
  **'기타 자산'**으로 보는 운영 관점을 우선하므로 그 관점에 맞춰 표기합니다 (§28.7).
- **Filing 후 잔액 이체**: 잔액은 카드 발행세액공제분이 아니라
  **적립액과 실제 납부세액의 차액 3,840,000원(연)** 입니다. 공제 신청 시 4,620,000원.
  이 이체는 사용자가 수동으로 해온 일이며, 자동화 여부는 미결입니다.
  자동화는 한국투자증권 API와 세금 일정, 이체 권한이 연결돼야 하므로 MVP 밖입니다.
- **카드결제금액 5,000,000원의 의미**: 카드 발행세액공제는 **매출**이 받은 금액을
  기준으로 합니다. 사용자가 카드%로 *지출*한 금액이라면 이 공제와 무관하고
  매입세액(세금계산서) 대상이 됩니다. 매출 기준임을 전제로 계산했습니다.

## 제약

- **하드코딩 색상 금지** (§28.4). 원시 값은 `tokens.css`의 `:root`에만 있고 나머지는 `var()`만 씁니다.
- **다크 모드 없음** (§28.4). MVP 제외. 추가 시 `theme.darkAlgorithm` 한 줄이면 충분합니다.
- **접근성** (§28.5). WCAG 2.1 AA, 포커스 표시 유지, 폼 라벨은 `for`/`id`로 연결,
  오류는 `role="alert"`. 키보드만으로 전 기능 이동이 가능해야 합니다.
- **antd 미사용**. 이 단계는 레이아웃 합의가 목적입니다. 컴포넌트 구현은 Issue 3에서 합니다.
- `login.html` 폼은 실제 전송 없이 `dashboard.html`로 이동합니다. 인증은 Issue 2 범위입니다.
