AssetFlow의 5개 역할 파이프라인을 순서대로 실행한다.

**요구사항:** $ARGUMENTS

## 넘기는 것과 넘기지 않는 것

이 구분이 파이프라인의 성패를 가른다.

| 단계 | 받는 것 | 받지 않는 것 |
|---|---|---|
| analyst | 요구사항 원문 | — |
| architect | 요구사항, analyst 출력 원문 | — |
| developer | 요구사항, analyst 출력 원문, architect 출력 원문 | — |
| **reviewer** | **AC, 대상 범위(SHA 또는 파일 목록)** | **개발자의 설명·판단 근거·"이렇게 짰습니다" 류 서술** |
| **tester** | **AC, reviewer 이슈 목록, 대상 범위** | **개발자의 설명·판단 근거** |

- 앞 단계 출력은 **원문 그대로** 넘긴다. 요약하면 근거가 사라진다
- developer 에는 analyst 의 AC 와 architect 의 설계를 **둘 다** 넘긴다
- **AC 는 "무엇을 요구받았는가"이므로 공유한다.** reviewer·tester 가 AC 충족을
  판정하려면 AC 가 있어야 한다. AC 없이 판정하게 하면 기준이 없는 통과가 된다
- **넘기지 않는 것은 "왜 그렇게 짐"이다.** 요구와 근거는 다른 층이다.
  근거를 넘기면 33.2 가 말한 대로 리뷰가 동의 확인으로 돌아간다

## 순서

1. **analyst** — AC 와 영향 범위 확보
2. **architect** — 파일 목록·계약 변경표·구현 순서. AC 없으면 여기서 되묻는다
3. **developer** — 설계대로 구현하고 검증 명령을 직접 돌린다
4. **reviewer** — `git status` + `git diff` 로 리뷰. Blocker 있으면 여기서 멈춘다
5. **tester** — 명령을 실제로 돌려 Go/No-Go

## 주의

- **untracked 파일을 빼먹지 마라.** 이 저장소는 새 파일을 만드는 변경이 많다.
  reviewer·tester 에게 범위를 넘길 때 `git status --porcelain` 의 `??` 항목까지
  포함하고, 그렇지 않으면 그 파일들은 리뷰되지 않은 채 통과된다
- 단계가 실패하면(AC 없음, Blocker 있음) 다음으로 넘어가지 말고 멈추고 보고한다
- 각 단계 출력을 사용자에게 그대로 보여준다. 생략하지 마라

## 완료 후

- **커밋하지 않는다.** `git status` 로 남은 것을 보여주고 멈춘다
  (`CONTRIBUTING.md` 는 `feature/*` 브랜치를 요구하므로 현재 브랜치도 확인해 보고한다)
- 무엇을 남겼는지, 무엇을 검증했고 무엇을 안 했는지 구분해 보고한다
- `.ai/session-log.md` 맨 위에 항목 추가를 **제안한다.** 기록 규약은 §32 다
