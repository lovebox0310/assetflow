변경분을 리뷰한다.

**대상 범위:** $ARGUMENTS

인자가 비었으면 staged + unstaged + **untracked** 를 대상으로 한다.

## 범위를 확정해서 두 에이전트에게 넘긴다

- `git status --porcelain` 과 `git diff --stat` 로 실제 대상을 먼저 구한다
- **untracked(`??`) 항목을 반드시 포함한다.** 이 저장소는 새 파일을 만드는 변경이
  많고, `git diff` 만 보면 그것들이 하나도 안 보인다. 누락되면 새 파일이
  리뷰되지 않은 채 통과된다
- 인자가 커밋 SHA 나 범위면 그것을 쓴다

## 넘기는 것

| 에이전트 | 넘기는 것 |
|---|---|
| reviewer | 대상 범위, **AC (있다면)** |
| tester | 대상 범위, reviewer 이슈 목록, **AC (있다면)** |

## 넘기지 않는 것

- **개발자의 설명, 판단 근거, "이렇게 짰습니다" 류 서술을 두 에이전트에게 절대 전달하지 마라.**
  그게 들어가면 리뷰가 동의 확인으로 바뀐다
- AC 는 "무엇을 요구받았는가"이므로 예외다. AC 가 없으면 없다고 말해라.
  에이전트가 기준 없는 통과를 하지 않도록 하는 것이 목적이다

## 순서

1. **reviewer** — `git status` + `git diff` 기준. 심각도 매기고 승인/보류
2. **tester** — reviewer 가 짚은 지점 + 회귀를 실제로 돌려 확인

## 완료 후

- Blocker / Critical 개수를 명시한다. 0개여도 명시한다(수정하지 않고 보고만)
- **AC 미제공이면 그것도 명시한다.** 판정 근거가 약해진 것을 숨기지 마라
- 승인이 나도 **직접 고치지 않는다.** 고치라고 하면 그때 developer 를 태운다
- 커밋하지 않는다
