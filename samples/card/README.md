# 카드사 엑셀 샘플 보관소

카드매입 내역을 엑셀로 올리는 기능의 근거 자료다. 실제 명세서는 **가공하지 않은
상태로 커밋하면 안 된다.** 이 폴더에는 익명화한 사본만 둔다.

## 왜 규격이 먼저인가

이 프로젝트에서 카드 데이터의 목적은 하나다. **§28.7 매입 대조**다.

```
카드 엑셀 → 매입세액 합계 → VAT 신고서 purchaseTax(320,000원)와 대조
                              → 어긋나면 지출 목록이 불완전하다는 근거
```

그래서 카드 엑셀은 "총 결제금액" 하나만으로는 쓸 수 없다. **공급가액(부가세 제외)**
와 **세액**이 분리돼야 역산이 산다. 이 구분을 §28.7 "부가가치세는 공급대가에서
난다" 원칙과 동일하게 적용한다.

| 규격 필드 | 필수 | 쓰이는 곳 |
|---|---|---|
| `approvedAt` 승인일자 | 예 | 거래 월 배정 |
| `merchantName` 가맹점명 | 예 | 미분류 사업비용 성분 추정(자동 분류 금지) |
| `supplyExVat` 공급가액 | 예 | 매입 공급가액 역산 |
| `vat` 세액 | 예 | 인정 매입세액 |
| `grossAmount` 공급대가 | 예 | `supplyExVat + vat` 교차 검증 |
| `installmentCount` 할부 | 아니오 | 원금/이자 분리(미구현) |
| `approvalNo` 승인번호 | 아니오 | 중복 적재 방지 키 |
| `taxKind` 세액구분 | 아니오 | 영세/면세 제외 |
| `reversal` 취소구분 | 아니오 | 매입취소 차감 |

필수 컬럼 분해가 안 되는 카드사는 **미지원**으로 명시한다. 그 값을 임의로 나누면
매입 대조가 틀어지므로, 모르면 모른다고 남기는 편이 낫다.

```
samples/card/

  lib/cfb.mjs               CFB(OLE2) 컨테이너 리더 — 암호화 여부 탐지용 (암호 읽기 없음)
  tools/
    inspect.mjs             샘플을 조사하는 도구 (파서가 아니다)
    lib/detect.mjs          매직 바이트로 실제 형식을 판별한다
    build-synthetic-xlsx.mjs 합성 xlsx 픽스처 생성기
    build-anonymized-samsung.mjs 삼성카드 합성 CSV 생성기
    build-anonymized-hyundai.mjs 현대카드 합성 CSV 생성기
    build-card-import-bundle.mjs 프로토타입용 파서 번들 생성기
    test-parse-samsung.mjs  삼성 파서 + 픽스처 재현성 검증
    test-parse-hyundai.mjs  현대 파서 + 픽스처 재현성 검증

```

## 프로토타입 화면과 파서는 번들로 잇는다

프로토타입(design/prototype)은 빌드·서버 없이 HTML 파일을 그대로 연다. 그런데
file:// 에서 ES 모듈은 막혀 파서를 직접 import 할 수 없다. 그렇다고 화면 안에
파서를 복사하면 "파서는 두 벌, 규격은 하나"가 깨진다.

- `tools/build-card-import-bundle.mjs` 가 진짜 원본
  (card-common.mjs, parse-samsung.mjs, parse-hyundai.mjs, card-columns.json)을
  읽어 `design/prototype/assets/card-import.js` 하나로 묶는다. `window.AFCard`
  로 노출한다.
- 모듈은 각자 IIFE 로 감싼다. 삼성과 현대 파서는 같은 이름의 내부 함수를
  가지는데 한 스코프에 풀면 나중 선언이 앞 것을 덮어써 삼성 합계 추출이
  조용히 현대 규칙으로 돌아간다(실제로 그 버그가 났다).
- 카드사 판별은 화면이 하지 않고 계약이 한다. `companies.*.detect` 의
  `headerSignature`(한쪽에만 있는 컬럼만)와 `minScore` 로 점수를 매기고,
  미만이면 카드사 미확인으로 거절한다. 공통 컬럼(이용일/카드번호/가맹점명/
  부가세)은 시그니처에 넣지 않는다.
- 번들에 암호 관련 코드는 없다(정책). 화면은 암호화 파일을 여지 않고
  CSV 로 안내한다.

## 카드내역 업로드 화면 (지출 화면)

`expenses.html` 에 "카드내역 가져오기" 섹션이 있다.

```
CSV 선택 → 매직 바이트 판별 → 카드사 판별 → 파싱 → 미리보기
  → 가맹점별 용도구분(규칙 저장) → 가져오기 → 가져온 카드내역 목록
```

- **형식 판별이 먼저다.** CFB(암호화 문서 또는 구형 .xls)면 "이 화면은 여지
  않는다. 카드사에서 암호화 없는 CSV 로 받거나 엑셀에서 다시 저장" 안내.
  평문 xlsx 도 미지원 안내. 비밀번호 입력란을 만들지 않는다 — 열기 구현이
  없는데 입력만 두면 사용자를 속인다.
- **미리보기는 가맹점 단위다.** 행마다 용도를 고르지 않고 가맹점별로 고른다
  (계약의 merchantRule). 고른 값은 규칙으로 저장되어 다음 명세부터 자동
  적용된다. 미분류로 되돌리면 규칙이 지워진다.
- **교차검증 결과를 표시한다.** 행 합계와 명세 합계행이 어긋나면 "이 파일을
  그대로 믿으면 안 된다"로 보여준다. 경고(vatExceedsGross, rowSkippedNoDate
  등)도 전부 보여준다.
- **rowKey 중복은 건너뛴다.** 같은 거래를 다시 가져오면 새로 저장하지 않고
  건너뜀 건수를 알린다.
- **합계는 행에서 다시 계산한다.** 저장 스냅샷에 합계 필드를 두지 않는다.
  저장합과 행이 어긋나는 원천을 차단한다.
- **미분류 행은 어느 합계에도 들어가지 않는다** (계약의 unclassifiedHandling).
- 가져온 내역마다 업무용 매입세액(부가세 순액)을 보여주지만, 카드만으로 매입
  대조가 완성되지 않는다는 knownGap 안내를 함께 둔다.

## 파서 공용 부품은 card-common.mjs 한 벌이다

CSV 파싱(RFC4180), 헤더 매칭, 금액 파싱, 카드번호 마스킹, 날짜 정규화는
`apps/frontend/src/lib/card/card-common.mjs` 의 한 벌을 쓴다. 삼성과 현대
파서가 각자 따로 두면 같은 규칙이 조금씩 어긋난다. 회사별로 다른 것 —
합계행 위치, 취소 판별, 날짜 형식, 금액 구조 — 은 각 파서가 책임진다.

## 픽스처는 반드시 생성기로 다시 만들어야 한다

`synthetic-sample.xlsx`가 한 번 **커밋돼 있는데 만드는 스크립트가 temp 에만 있던
상태**로 있었다. 바이너리 픽스처만 남으면 아무도 내용을 모르고, 바꿀 수도 없다.
temp 를 정리하자 그 테스트가 그대로 깨졌다.

지금은 두 규칙으로 이 재발을 막는다.

- `anonymized/` 의 모든 픽스처는 같은 폴더의 `build-*.mjs` 로 만든다.
- 파서 시험(`test-parse-samsung.mjs`, `test-parse-hyundai.mjs`)이 생성기를 다시
  돌려 **바이트 단위로 같은지** 비교한다. 한 바이트라도 다르면 실패한다.
  손으로 고친 픽스처는 이 검사에서 걸린다.

## 삼성카드는 CSV 로 확인했다

암호화 xlsx 는 여전히 못 읽는다. 하지만 삼성카드는 같은 명세서를 **암호화 없는
CSV 로도** 내준다. 그쪽에서 규격을 확정했다.

```
파일      samsungcard_detail_202601(개인사업자용 카드이용내역서).csv
인코딩    UTF-8 BOM, 41행 x 12열
헤더      R19 (앞 18행은 안내문)
거래      R20~R37 = 18건
합계      R15 (거래보다 앞에 있다)
```

헤더는 카드사 문구 그대로다.

```
상품 | 매출 | 성명 | 카드구분 | 카드번호 | 이용일 | 이용금액(원) | 부가세(원)
     | 가맹점명 | 승인번호 | 사업자번호 | 업종
```

이걸 계약에 옮기면서 생긴 결정 세 가지:

**1. `supplyExVat` 컬럼이 없다.** 삼성은 공급가액을 안 준다. 카드 총액과 부가세만
주므로 공급가액은 **역산**한다.

```
supplyExVat = grossAmount - vat
```

`vat` 이 10% 로 역산한 공급가액을 1원 단위 반올림한 값이라 이 식이 성립한다.
실제 18건 전부에서 오차 1원 이내로 맞는다. 컬럼을 임의로 나누지 않고 빼기로
구하므로 매입 대조가 흔들리지 않는다. 계약에서는 `source: "columnOrDerived"`
로 표시해 "컬럼이 없어도 파생된다"를 명시한다.

**2. `approvalNo` 는 유일하지 않다.** 같은 번호가 양수·음수 두 번 나온다. 재승인쌍이다.
그래서 중복 적재 방지에 `approvalNo` 하나를 쓰면 안 되고 거래 묶음 키로 쓴다.

```
rowKey = approvedAt | merchantName | grossAmount | vat | approvalNo | cardMasked
```

**3. 취소 컬럼이 없다.** 대신 금액이 음수다. `grossAmount < 0` 이면 `매입취소`로
표시한다. 실제 파일에 2건 있다.

합계는 반드시 교차검증한다. 18건의 합계 `2,385,860`, 부가세 `8,453` 이 명세서의
합계행과 정확히 일치한다. 합계행은 거래에 더하지 않는다.

```
카드 엑셀 → 18건 행 합계 vs 명세 합계행 → 다르면 파싱 버그로 단정한다
```

## 현대카드는 승인 금액과 이용 금액이 다르다

현대카드도 암호화 없는 CSV 를 준다. 실제 파일로 확정한 사실이다.

```
파일      hyundaicard_202605041336031708166977_1070(Sheet0).csv
인코딩    UTF-8 BOM, 1,335행 x 11열
헤더      R8 (앞 7행은 제목·기간·회원정보)
거래      R9~R1331 = 1,323건 (2025년 1년 전체)
합계      R1332 — 삼성과 반대로 데이터 뒤에 있다
금액      천단위 콤마를 따옴표로 감싼다("139,000") — 단순 split 으로 열이 깨진다
```

```
이용일 | 카드번호 | 가맹점명 | 승인 금액 | 이용 금액 | 부가세
       | 관계 | 할부 | 상태 | 가맹점번호 | 사업자등록번호
```

삼성과 다른 결정 다섯 가지:

**1. 금액이 세 개다.** 승인 금액(합계 49,283,063), 이용 금액(47,533,063), 부가세
(1,487,321)을 별도로 준다. 규격의 `grossAmount` 는 **이용 금액**(청구 기준)에
묶는다. 승인 금액은 새 필드 `approvedAmount` 다. 계약의 grossAmount 별칭에서
"승인금액" 을 뺀 이유다 — 헤더 매핑은 같은 별칭을 처음 등록한 필드에 묶으므로,
별칭을 그대로 두면 grossAmount 가 승인 금액에 잘못 붙었을 것이다.

**2. 부가세는 가맹점 신고값이다.** 이용금액/11 로 검산하면 1,323행 중 838행이
어긋난다. 포인트 결제·면세·가맹점 측 계산이 섞여 있어서다. 그래서 현대 파서는
삼성처럼 부가세를 검산하지 않는다. 검산하면 거짓 경고가 838건 나온다. 부가세
컬럼은 그대로 믿고, 합계(1,487,321)가 합계행과 맞는지로 검증한다 — 실제로
정확히 일치했다.

**3. 취소는 상태 컬럼으로 판별한다.** 삼성은 취소 컬럼이 없어 음수로 판별했지만
현대는 `상태`(정상/취소)를 준다. 23건 취소가 음수 23건과 정확히 일치해서
교차검증이 되고, **부가세가 -2,445 인 취소 행**도 있으므로 컬럼이 우선이다.

**4. 포인트 결제 행이 있다.** 승인≠이용 30건 중 28건은 이용=0(포인트 전액),
2건은 부분 결제다. 이용=0 인데 부가세>0 인 행 17건은 역산 공급가액이 음수가
된다. 파서는 값을 자르지 않고 `vatExceedsGross` 경고를 낸다. 조용히 0으로
자르면 부가세 합계와 대조가 어긋난다.

**5. 승인번호가 없다.** 그리고 같은 날짜·가맹점·금액·부가세·카드·상태가 전부
같은 행이 실제로 13그룹 있다(카드사 자신도 구별 못 한다). rowKey 는 내용 +
동일내용 발생차수(#n)로 유일성을 만든다. 내용이 같은 행의 순서가 바뀌어도
키 집합이 같아서 재임포트 중복 제거가 유지된다.

주의: 현대는 카드번호를 **전체 번호로** 준다(삼성은 이미 마스킹된 값을 준다).
파서가 `maskCardNumber` 로 가리고 원본은 어디에도 남기지 않는다. 회원정보 행
(성명·생년월일)도 파싱해서 버린다.

날짜는 `YYYY.MM.DD` 점 구분이므로 ISO(YYYY-MM-DD)로 정규화한다. 관계(본인 732/
가족 591)와 할부(6건)는 데이터로 넘기되 분류 판정에는 쓰지 않는다 — 용도
구분은 여전히 사용자가 정한다.

교차검증: 1,323행의 합계(이용 47,533,063 / 부가세 1,487,321 / 승인 49,283,063)
와 건수 1,323이 합계행과 정확히 일치한다.

## 용도 구분은 파일에 없고 사람이 정한다

삼성 CSV 에는 업무용/개인용 구분이 없다. 카드사는 분류하지 않는다. 그런데
아파트관리비는 매입세액에 들어갈 업무용 지출이다. 그래서 **기본값을 정하지 않는다.**

| 값 | 뜻 |
|---|---|
| `unclassified` | 기본값. 아직 사람이 정하지 않음 |
| `business` | 업무용. 매입세액 소급 대상 |
| `personal` | 개인. 매입세액 불인정 |

- 파서는 **항상 `unclassified` 로 낸다.** 자동 분류하지 않는다.
- 행마다 사용자가 고르고, 반복되는 가맹점은 규칙으로 저장한다.
- 이 필드는 `source: "user"` 다. 그래서 헤더 탐색 대상도 아니고,
  파일에 없다는 이유로 '필수 필드 누락' 판정이 되지 않는다.
  (`inspect.mjs` 와 파서가 이 구분을 지키지 않으면 실제 파일이 전부 실패한다)


## 명세서는 통상 암호화되어 온다

삼성카드에서 받은 실제 파일이 이러했다.

```
파일명        samsungcard_detail_202601.xlsx   (.xlsx 라고_extension)
실제 형식     CFB(OLE2) 컨테이너, 암호화된 OOXML
암호화        ECMA-376 Agile Encryption 4.4 / 비밀번호 기반
```

**확장자를 믿으면 안 된다.** `.xlsx` 는 zip 인데 이 파일은 zip이 아니어서
"zip 이 아니다" 같은 원인이 보이지 않는 오류만 난다. 그래서 도구는 확장자가 아니라
**매직 바이트**로 형식을 먼저 판별한다.

## 암호화 정책 (사용자 결정)

암호화 파일은 **사용자가 입력한 정확한 비밀번호로 열리는 경우**와
**이미 암호가 풀린(평문) 파일**만 읽는다.

- 암호 입력만 허용한다. 원본 파일과 비밀번호는 서버로 보내지 않는다
- 비밀번호가 맞지 않으면 "비밀번호가 틀렸습니다"만 알리고 끝낸다
- 재시도 루프, 대입, 우회 등 **풀어서 해결하려는 어떤 로직이나 시도도 만들지 않는다**
- 이전에 이 방향으로 만든 암호 구현(해시 키 유도, 패딩 없는 AES-CBC 등)은
  **전부 백지화했다.** `apps/frontend/src/lib/card/` 에는 파서만 남아 있다
- 비밀번호를 모르면 카드사에서 암호화 없는 CSV 로 받거나,
  엑셀에서 열어 암호화 없이 다시 저장한 파일을 올린다

## 카드사 샘플 추가 절차

1. **원본을 이 폴더에 두지 않는다.** 원본은 작업 폴더 등 로컬에만 둔다.
2. 아래 「익명화 체크리스트」를 모두 통과시킨다.
3. `anonymized/`에 `카드사-용도-기간.xlsx` 이름으로 넣는다.
   예: `삼성카드-매출내역-202609.xlsx`
4. 조사 도구를 돌려 헤더와 합계 행 패턴을 확인한다.
   ```
   node samples/card/tools/inspect.mjs samples/card/anonymized/삼성카드-매출내역-202609.xlsx
   ```
   암호화 파일이면 `형식 판별`까지만 되고 헤더는 못 읽는다. 이때는
   ① 비밀번호를 입력받아 열거나 ② 엑셀에서 암호화 없이 다시 저장한다.
5. `card-columns.json`의 `companies`에 카드사 프로파일을 추가한다.
   헤더 이름이 다르면 `headerAliases`에, 합계 행 표현이 다르면
   `rowRoles.grandTotal`에 **실제 문자열 그대로** 적는다.
6. 매핑이 안 되는 열이 있으면 추측해서 채우지 말고 그대로 남긴다.

## 익명화 체크리스트

커밋 전에 전부 확인한다. 하나라도 빠지면 커밋하지 않는다.

- [ ] 카드번호 전부 제거 (`1234-****-****-3456` 형태로 가린다)
- [ ] 회원명·생년월일·연락처 제거
- [ ] 가맹점명을 실제 상호로 두지 않는다 (`OO컴퓨터`처럼 가린다)
      - 단, 비용 성분 추정에 가맹점명이 쓰이므로 **형태는 유지**한다
        (길이, 한글/영문/숫자 혼합 여부)
- [ ] 승인번호 제거 또는 치환
- [ ] 지점명·지번 등 위치 정보 제거
- [ ] 파일 메타데이터(작성자, 경로) 제거
      - 엑셀은 문서 속성에 작성자명이 남는다. 저장 시 확인한다
- [ ] `외국계/캐피탈` 구역은 금액만 두고 가맹점명을 가린다

실제 금액이 그대로 남아 있으면 매입 대조 검증에 쓸 수 없으니, 합성 금액으로 바꾼다.
합성 샘플은 `build-synthetic-xlsx.mjs`로 만든 `synthetic-sample.xlsx`를 기준으로
삼는다. CSV 쪽 합성 명세서는 `build-anonymized-samsung.mjs`가 만든
`samsungcard-personal-anon.csv`다.

### 커밋 차단 기준

- `samples/card/` 바로 아래에 놓인 엑셀/CSV는 **전부 차단**된다.
  익명화 체크리스트를 아직 안 거친 것으로 간주한다.
  실수로 `samsungcard_detail_202601.xlsx` 같은 이름으로 내려받아 커밋되는 것을 막는다.
- `samples/card/anonymized/`는 추적 대상이다. 여기에 있는 파일은
  체크리스트를 통과했다고 간주하므로 확장자 제한이 없다.
- `samples/card/raw/`, `*-raw.*`, `*-original.*`, `*-실명.*`, `*카드번호*` 는
  경로와 무관하게 차단된다.

## 파서는 두 벌, 규격은 하나

FE는 SheetJS로 **미리보기**, BE는 Apache POI로 **검증·저장**을 맡는다. 양쪽에
파서 규칙이 두 벌 생기므로 **판정 기준은 `card-columns.json` 한 곳에만 둔다.**

- FE: 원본 파일이 서버로 올라가지 않고 표를 먼저 보여준다
- BE: 정규화된 행만 받아 규격·검증식을 통과한 뒤 저장한다
- **사용자가 확인·승인하기 전에는 BE가 어떤 값도 확정하지 않는다**

규격(`card-columns.json`)을 고칠 때 FE 파서와 BE 파서를 **같은 PR에서 함께** 고친다.
한쪽만 고치면 미리보기와 실제 저장 결과가 어긋난다.

## 아직 정하지 않은 것

- 할부 결제를 현금흐름에 반영할 때 원금/이자 분리 규칙
- 경비율계산세액의 실제 지급세액과의 차이 처리
- 카드사별 파일 변경 이력(같은 카드사가 매달 헤더를 바꾸는지)
- .xls(구형) 지원 여부 — POI는 가능하지만 SheetJS는 별도 처리가 필요하다
- 비밀번호를 브라우저에 얼마나 오래 두는지(사이드이딩 vs 서버와 세션만)
- 잘못된 비밀번호를 여러 번 시도했을 때 잠금/지연 정책

## 아직 없는 것

- **암호화 파일을 여는 경로.** 정책은 정해졌다: 암호 입력만 허용하고, 틀리면
  우회 없이 실패를 알린다. 그 구현(비밀번호 입력 UI와 실제 여는 동작)은
  아직 없다. 그때까지 암호화 xlsx 는 형식 판별까지만 가능하다.
  실무 경로는 이미 열려 있는 파일이다 — 암호화 없는 CSV 나 엑셀에서
  다시 저장한 평문 xlsx.
- SheetJS 미리보기 UI, POI 파서, 업로드 API 모두 미구현.
- xlsx 로 받은 삼성 명세서의 헤더가 CSV 와 같은지는 열어 본 후에 확인한다.
  CSV 에서 확정한 프로파일은 `card-columns.json` 의 삼성카드 항목으로
  반영돼 있다. 헤더가 다르면 `headerAliases` 를 추가하면 된다.
- 현대카드는 CSV 만 확인했다. xlsx 로 받으면 형식(암호 여부 포함)을 다시
  조사한다. 파일명에 `(Sheet0)` 이 붙는 건 발급 시점마다 다를 수 있다.
